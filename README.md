# S09. SAST, секреты и решения по находкам

Учебный Notes API на C#/.NET 10. На занятии запускаем два анализатора, проверяем их сигналы по коду и истории, исправляем подтверждённый дефект и повторяем проверку. Здесь намеренно есть небезопасный код. Используйте локальный стенд на `localhost`.

## Подготовить до занятия

- Windows, VS Code, Git и .NET SDK **10.0.401**; `global.json` закрепляет SDK с допуском следующих исправлений 10.0.4xx.
- Docker Desktop с запущенным Linux Engine. Docker нужен для анализаторов; API запускается обычным `dotnet run`.
- Для кнопок в `requests.http` — расширение VS Code **REST Client** (`humao.rest-client`). Альтернатива — PowerShell-команды ниже.
- Интернет нужен для первоначального `dotnet restore` и загрузки образов. Анализаторы работают с локальными правилами, без учётной записи и сети внутри контейнера.

Откройте в VS Code именно папку этого репозитория: **File → Open Folder → s09-sast-secrets**. Затем **Terminal → New Terminal**, профиль **PowerShell**. Все команды ниже выполняются из корня этой папки. Если ZIP распакован рядом с другими папками комплекта, это не весь `S09_ready_v1_0`, а вложенная `s09-sast-secrets`.

```powershell
dotnet --version
git --version
docker version
dotnet restore NotesApi.slnx --locked-mode
dotnet test NotesApi.slnx --no-restore
docker pull semgrep/semgrep:1.175.0@sha256:b94b53d02fd4a022f9eac4e2af1380f5c3c4c21400e79d3336bdff1d1db5e796
docker pull ghcr.io/gitleaks/gitleaks:v8.30.1@sha256:c00b6bd0aeb3071cbcb79009cb16a60dd9e0a7c60e2be9ab65d25e6bc8abbb7f
```

Ожидается **4 passed, 1 skipped**. Пропущен специально подготовленный негативный тест; это не доказательство отсутствия уязвимости. Обе секции `docker version`, Client и Server, должны быть доступны. Образы закреплены по digest; без явного обновления не заменяйте их на `latest`.

## 1. Получить сигнал SAST

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\record-source.ps1 -Label before
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\scan-sast.ps1 -Label before
code .\reports\local\semgrep-before.json
```

`ExecutionPolicy Bypass` относится только к запускаемому дочернему процессу PowerShell, системная политика не меняется. Скрипты можно предварительно прочитать в VS Code. Команда `code` открывает файл; если CLI VS Code недоступен, найдите его в Explorer слева.

Для исходной версии ожидается **8 сигналов** на трёх `.cs`-файлах. У записи есть `check_id`, `path`, `start.line`, `extra.message`. Переходите по пути и строке, затем проверяйте входные данные, назначение и достижимость кода. Два сигнала могут указывать на одну причину: число записей не равно числу дефектов.

`semgrep.yml` содержит пять маленьких учебных правил. Они намеренно ограничены синтаксисом; это не полный профиль промышленного SAST. `sql-commandtext-assignment` требует просмотреть любое присваивание SQL, `sql-commandtext-concat` выделяет конкатенацию. Наличие этих сигналов само по себе не доказывает SQL-инъекцию. Вывод об уязвимости требует анализа потока и сценария.

## 2. Проверить поведение API

В первом терминале:

```powershell
dotnet run --project src/NotesApi --urls http://localhost:8080
```

Дождитесь `Now listening on: http://localhost:8080`. Терминал занят сервером — оставьте его работающим. Откройте **второй** терминал PowerShell. В нём:

```powershell
Invoke-RestMethod http://localhost:8080/health
Invoke-RestMethod 'http://localhost:8080/notes/search?q=note' -Headers @{'X-User'='alice'} | ConvertTo-Json
$payload = [Uri]::EscapeDataString("%' OR 1=1 -- ")
Invoke-RestMethod "http://localhost:8080/notes/search?q=$payload" -Headers @{'X-User'='alice'} | ConvertTo-Json
```

В чистой базе обычный поиск Alice возвращает одну её заметку; последний запрос позволяет проверить, возвращаются ли чужие записи. Проверяйте владельца и содержимое, а не только HTTP 200. Заголовок `X-User` — учебный переключатель, не настоящая аутентификация.

Вместо консоли можно открыть `requests.http` и щёлкнуть **Send Request** непосредственно над строкой `GET` соответствующего блока. Это ссылка расширения REST Client, а не команда терминала. Сначала запрос 0, затем 1 и 2; ответ откроется в отдельной вкладке справа. Если ссылки нет, установите REST Client и снова откройте файл.

Перед изменением кода и запуском тестов вернитесь в первый терминал и нажмите **Ctrl+C**. На Windows запущенный процесс может блокировать пересборку. Тесты запускают собственный сервер и отдельную временную БД для каждого теста, работающий порт 8080 им не нужен.

## 3. Посмотреть секрет в настоящей истории

ZIP исходников обычно не содержит `.git`. Для этого опыта есть маленький `fixtures/secret-history.bundle`: полноценная Git-история из трёх коммитов, без действующих учётных данных. Она разворачивается в отдельную соседнюю папку:

```powershell
git clone .\fixtures\secret-history.bundle ..\s09-secret-history
git -C ..\s09-secret-history log --oneline --all
git -C ..\s09-secret-history ls-tree -r --name-only HEAD
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\scan-secrets.ps1 -Mode tree
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\scan-secrets.ps1 -Mode history
code .\reports\local\gitleaks-history.json
```

Если `s09-secret-history` уже существует, сначала убедитесь, что это именно прежняя учебная копия. Повторно клонировать не нужно; скрипт ничего не удаляет. Для нового опыта выберите другую родительскую папку для всего комплекта.

В текущем дереве — **0** сигналов, в истории — **1**. В raw-отчёте значение замаскировано; важны `RuleID`, `File`, `StartLine`, `Commit` и `Fingerprint`. Commit относится к **отдельной истории**, не к версии Notes API. Для поиска коммита используйте `git -C ..\s09-secret-history show --stat <Commit>`. Строка `<Commit>` — место для фактического хеша из отчёта, угловые скобки не вводятся.

Правило `.gitleaks-training.toml` распознаёт только специально фиктивный формат этого опыта. Оно не заменяет штатные правила поиска настоящих секретов в вашем проекте. Сканируется вся доступная история примера (`--all`), а не история родительского учебного репозитория.

Для настоящего секрета порядок такой: ограничить последствия и **отозвать/заменить секрет у его владельца**, проверить использование и затронутые сервисы, затем согласованно очищать историю и доступные копии, добавить предотвращающие проверки. Удаление строки новым коммитом не отзывает полномочия. В нашем примере никакого внешнего отзыва не происходит: значение фиктивное. Переписывание общей истории в этом упражнении не требуется.

## 4. Исправить, проверить и связать свидетельства

1. Сохраните исходный отчёт и версию файлов. Если репозиторий клонирован с GitHub, запишите `git rev-parse HEAD` и `git status --short`; для ZIP используется SHA-256 в `reports/local/source-before.json`.
2. Обоснуйте статус одного подтверждённого сигнала. Покажите, откуда приходят данные и какое свойство нарушается.
3. В `tests/NotesApi.Tests/NotesTests.cs` замените только `[Fact(Skip = "S09: включить до исправления SQL.")]` на `[Fact]`.
4. Запустите `dotnet test NotesApi.slnx --no-restore`: ожидается **4 passed, 1 failed**. Отчёт анализатора дополняется воспроизводимым проявлением.
5. Исправьте причину в `Search`. Сохраните штатный поиск и передачу пользовательских значений как данных.
6. Снова запустите тесты: должны пройти все **5**. Сохраните результаты и версию исправления.
7. Повторите анализ:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\record-source.ps1 -Label after
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\scan-sast.ps1 -Label after
dotnet test NotesApi.slnx --no-restore --logger 'trx;LogFileName=after.trx' --results-directory reports/local/tests-after
```

Количество сигналов может не обнулиться: широкое правило продолжает требовать просмотра безопасного SQL. Отсутствие сигнала узкого правила и прохождение негативной/регрессионной проверок отвечают на разные вопросы. Не выключайте правило только для получения нуля.

При повторном ручном запуске API проверьте обычный и изменённый запросы ещё раз. Пустой результат атаки допустим; пустой результат штатного поиска — нет. Подробная форма цепочки и реестра публикуется в основном репозитории курса вместе с S09.

## Что оставить после занятия

Краткий реестр решений по сигналам и одну цепочку: конфигурация/область и версия → запуск → исходный finding → интерпретация → решение/изменение → тесты → rerun с версией. Отдельный большой отчёт по каждому анализатору не нужен. Находки с одной причиной связывайте, не размножайте дефекты ради количества.

После пары перенесите процесс на собственный проект, используя подходящие языку SAST-правила и штатный профиль секретов. Не добавляйте намеренно секреты или дефекты в командный проект. Если подтверждённых сигналов нет, сохраните запуск и обоснования решений; не выдумывайте finding.

## Если инструмент пока недоступен

В `reports/semgrep-before.json` и `reports/gitleaks-history.json` лежат **настоящие** сохранённые отчёты. Их происхождение и хеши исходников — в `reports/provenance.json`, пояснения — в `reports/README.md`. По ним можно тренировать анализ сигнала и разбор кода. Чужой сохранённый отчёт нельзя выдавать за собственный запуск: технический запуск и rerun нужно доработать после восстановления окружения.

SDK/restore: проверьте версию из `global.json` и доступ к NuGet. Ошибка Docker Engine: запустите Docker Desktop и выберите Linux containers. Порт занят: остановите прежний учебный API. Несовпадение строк после редактирования ожидаемо — ищите правило и функцию, а не фиксированный номер строки. Ошибки разбора Semgrep или аварийное завершение анализатора не считаются отсутствием находок.

## Проверенные границы комплекта

Код, тесты, правила, Git bundle и сохранённые отчёты проверены на Linux с .NET SDK 10.0.401, Semgrep CE 1.175.0 и Gitleaks 8.30.1. Образы опубликованы и проверены по реестрам. Запуск Docker-контейнеров и Windows PowerShell в среде подготовки не выполнялся; ведущий должен пройти короткую репетицию на своей Windows до занятия.
